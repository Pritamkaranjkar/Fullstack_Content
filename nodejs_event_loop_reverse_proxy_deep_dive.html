02 · What exactly is Node.js?

Node.js lets you execute JavaScript outside the browser. It combines the V8 JavaScript engine with operating-system and networking capabilities.

01 — RUNTIME

JavaScript runtime

Node is an environment in which JavaScript can run. It is not a new language. Your JavaScript is executed by V8.

02 — SYSTEM ACCESS

Backend capabilities

Node exposes APIs for HTTP, files, processes, streams, timers, networking and other server-side tasks.

03 — ASYNC MODEL

Non-blocking I/O

Node is designed so your JavaScript does not have to sit idle while network or I/O operations are in progress.

04 — IMPORTANT LIMIT

Not “single-threaded everything”

The JavaScript execution model is centered around one main thread per Node process, while Node/libuv and the OS can perform other work outside that JavaScript execution path.

Minimal HTTP server
const http = require("http");

const server = http.createServer((req, res) => {
  res.end("Hello from Node.js");
});

server.listen(3000, () => {
  console.log("Server listening on port 3000");
});
What happened? Node creates a server, starts listening on port 3000, and invokes your request handler when an HTTP request is ready to be processed.

04 · The Event Loop

The Event Loop is the heart of Node's asynchronous programming model. It lets one JavaScript thread keep moving instead of waiting synchronously for every I/O operation.

05 · Async I/O: the request does not “wait” the way you think

Database-style example
app.get("/users", async (req, res) => {
  const users = await db.query("SELECT * FROM users");
  res.json(users);
});
Important: await suspends the current async function's continuation until the Promise settles; it does not mean the entire Node process synchronously freezes waiting for the database.

While DB request is pending

Node can process other incoming events and run other ready JavaScript. The database server is doing database work independently.

When DB finishes

The Promise settles. The continuation after await becomes eligible to run, and eventually your response code executes.

Rule: Node's strength is not “JavaScript is magically parallel.” Its strength is avoiding unnecessary blocking while waiting for I/O.

06 · Event Loop phases

A simplified mental model of Node's loop is enough for most backend work. The real implementation has more detail, but these phases explain the common behavior.

Timers

Handles callbacks whose timers have become eligible, such as setTimeout() and setInterval().

Pending callbacks

Processes certain callbacks deferred from previous operations.

Poll

Processes I/O-related callbacks and may wait for I/O when appropriate.

Check

Runs setImmediate() callbacks.

Close callbacks

Handles some close events, such as socket close callbacks.

Microtasks

Promise reactions and Node's process.nextTick() mechanism have special scheduling behavior and should be understood separately.

07 · Microtasks: Promise callbacks and nextTick

console.log("A");

Promise.resolve().then(() => {
  console.log("B");
});

setTimeout(() => {
  console.log("C");
}, 0);

console.log("D");
Typical output: A → D → B → C. Synchronous code finishes first; Promise reaction work is handled as microtask work before the timer callback gets its turn.

Microtask

Promise reactions are scheduled as microtasks. They are not simply another ordinary timer callback.

process.nextTick()

Node gives process.nextTick() special treatment. Excessive recursive nextTick scheduling can starve I/O, so use it carefully.

08 · Blocking vs non-blocking

Non-blocking style

const fs = require("fs");

fs.readFile("large.txt", "utf8", (err, data) => {
  console.log(data);
});

console.log("Server can keep moving");

The file operation is initiated and its callback runs later. The current JavaScript execution can continue.

Blocking style

const fs = require("fs");

const data =
  fs.readFileSync("large.txt", "utf8");

console.log(data);

The synchronous call keeps the JavaScript execution occupied until it completes. On a server, repeated blocking operations can damage throughput.

Important: “Node is single-threaded” does not mean “Node can never use other threads.” It means your main JavaScript execution model is centered on one thread per process. Worker threads and libuv's worker pool exist for specific workloads.

10 · Reverse Proxy

A reverse proxy sits in front of your application servers. The client talks to the proxy; the proxy talks to your internal application.

Browserexample.com
→
Reverse Proxypublic entry point
→
Node.jsinternal :3000

TLS / HTTPS

The proxy can terminate HTTPS and forward traffic to an internal application connection.

Routing

It can route different paths or hosts to different backend services.

Load balancing

It can distribute traffic across multiple application instances.

Static assets

It can serve static content without involving Node for every request.

Headers & limits

It can apply request-size limits, headers, compression and related edge controls.

Isolation

Your Node process can remain on a private port/network while the proxy exposes the public interface.

13 · Why Redis matters when you have multiple Node processes

Node #1its own process memory
Node #2different process memory
Node #3different process memory
↓ shared external state
Redisshared cache / sessions / temporary state

If you keep a variable in Node process memory, another Node process does not automatically see it. This matters once you scale to multiple instances.

// Process #1
let count = 10;

// Process #2
// `count` is not automatically the same variable.

External stores such as Redis can provide shared state when the application architecture needs it.

14 · Final mental model

1
User sends request.
The public request reaches your infrastructure.
2
Reverse proxy receives it.
It can terminate HTTPS, apply edge rules and choose a backend.
3
Node receives the request.
Your JavaScript handler runs on the Node process's main JavaScript execution thread.
4
Node starts I/O.
Database/network/file operations can proceed asynchronously rather than blocking the JS thread.
5
Event Loop keeps processing eligible work.
Other requests can make progress while I/O is pending.
6
I/O completes.
The relevant callback or Promise continuation becomes ready.
7
Node produces response.
The response travels back through the proxy to the user.
Remember: Reverse proxy ≠ Event Loop. The reverse proxy manages traffic at the server boundary. The Event Loop manages asynchronous JavaScript execution inside a Node process.

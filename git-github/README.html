Git & GitHub — Complete Student Guide

Learn version control from the first command to real team collaboration.

This guide is designed to be used during practical teaching. Each important concept includes what it means, when to use it, commands, a step-by-step case, and a practice task.

How to use this guide: Do not only read the commands. Open a terminal, create a small practice project, and run the commands yourself. Git becomes easy when you understand what changes after every command.

1. What is Git?

Git is a version control system. It records changes made to files so that developers can track work, create versions, work on separate features, and recover previous states.

Why do we need Git?

  • Track changes in a project.
  • Know who changed something and when.
  • Save working versions of a project.
  • Work on features without disturbing the main code.
  • Combine work from multiple developers.
  • Recover from mistakes.
Real-life example: Imagine writing an assignment and saving it as assignment-final.docx, assignment-final-2.docx, assignment-final-real.docx. Git solves this version-management problem properly.

2. What is GitHub?

GitHub is a platform for hosting Git repositories online. It adds collaboration and project-management features around Git.

GitGitHub
Software installed on your computer.Online platform for repositories and collaboration.
Tracks project history locally.Stores and shares repositories remotely.
Works without internet for most local operations.Used to collaborate, review, share, and host code online.
Local Project → Git Repository → GitHub Remote Repository → Team Collaboration

3. Install and Verify Git

git --version

If Git is installed, the command displays the installed Git version.

Practice: Run git --version and note the version shown on your computer.

4. First-Time Git Configuration

Git uses your name and email when creating commits.

git config --global user.name "Your Name"
git config --global user.email "you@example.com"

Check the configuration

git config --global --list
Important: The email used for Git commits should be configured thoughtfully. If you want GitHub to associate commits with your GitHub account, use an email configured for that account or the appropriate GitHub-provided no-reply address.

5. Git Repository — What is it?

A Git repository is a project whose history is managed by Git. When you run git init, Git creates a hidden .git directory containing repository information.

6. Case 1 — Start Git in an Existing Project

Use this when: You already have a project on your computer and want to start tracking it with Git.

Step 1 — Open the project

cd path/to/my-project

Step 2 — Initialize Git

git init

Step 3 — Check status

git status

Step 4 — Stage files

git add .

Step 5 — Create the first commit

git commit -m "Initial commit"
Working Directory → git add → Staging Area → git commit → Git Repository

9. Case 2 — Make a Change and Commit It

  1. Edit a file.
  2. Run git status.
  3. Review the change with git diff.
  4. Stage the file.
  5. Review the staged change.
  6. Commit it.
git status
git diff
git add index.html
git diff --staged
git commit -m "Update homepage"
Practice: Create index.html, commit it, modify the heading, and create a second commit.

10. Commit Messages

A commit should describe the change clearly.

Good examples:

git commit -m "Add login form"
git commit -m "Fix navbar spacing"
git commit -m "Add responsive product cards"

Avoid messages such as:

git commit -m "changes"
git commit -m "update"
git commit -m "final"

11. Case 3 — Create a GitHub Repository and Push an Existing Project

Use this when: your project exists locally and you now want to publish it to GitHub.

Step 1 — Create an empty repository on GitHub

Create the repository on GitHub. If your local project already has its own commits, it is simplest for beginners to create the remote repository without adding an unrelated initial README or other starter files.

Step 2 — Connect the local repository to GitHub

git remote add origin https://github.com/USERNAME/REPOSITORY.git

Step 3 — Check the remote

git remote -v

Step 4 — Push the branch

git branch -M main
git push -u origin main
Local Repository → origin → GitHub Repository
Do not upload secrets. Never commit passwords, API keys, private keys, database credentials, .env files containing secrets, or other sensitive credentials.

12. .gitignore

.gitignore tells Git which files or folders should normally not be tracked.

Example for a Node.js project:

node_modules/
.env
.next/
dist/
build/
coverage/
.DS_Store

After creating or changing .gitignore:

git status
Important: .gitignore does not automatically remove a file that Git is already tracking. If a secret was already committed, simply adding it to .gitignore is not enough; the secret may still exist in Git history and may need proper credential rotation and history cleanup.

13. Clone — Get an Existing Repository

Use this when: the project already exists on GitHub and you want a local copy.

git clone https://github.com/USERNAME/REPOSITORY.git
cd REPOSITORY

Cloning normally creates the local repository, working files, and a remote named origin.

14. Case 4 — Start Working on an Existing Team Project

git clone https://github.com/COMPANY/PROJECT.git
cd PROJECT
git status
git branch
git remote -v

Before starting new work, update your local branch as appropriate for the team's workflow.

git pull

15. Branches

A branch gives you a separate line of development. Branches are commonly used for features, bug fixes, experiments, and other focused work.

See branches

git branch

Create a branch

git switch -c feature-login

Switch branches

git switch main
git switch feature-login

Delete a merged local branch

git branch -d feature-login
Recommended beginner habit: Keep main stable and create a separate branch for new work.

16. Case 5 — Feature Branch Workflow

Suppose the team asks you to add a login page.

git switch main
git pull
git switch -c feature/login-page

Now develop the feature.

git status
git add .
git commit -m "Add login page"

Publish the branch:

git push -u origin feature/login-page

Then open a Pull Request on GitHub for review.

main → feature/login-page → commit → push → Pull Request → review → merge

17. Remote Repositories

A remote is a saved name for another Git repository, commonly a GitHub repository.

git remote -v
git remote add origin URL
git remote remove origin
git remote rename origin upstream

origin is only a conventional name. It is not a special Git keyword; it is simply the default name commonly assigned to the repository you cloned from or added as the primary remote.

18. Fetch vs Pull

git fetch

Downloads information from a remote repository without integrating those changes into your current branch.

git fetch origin

git pull

Fetches remote changes and then integrates them according to the configured pull behavior.

git pull
Easy rule: Fetch = bring remote information down and inspect it. Pull = fetch + integrate.

19. Case 6 — Your Teammate Pushed Changes

If your teammate pushed changes to the shared branch and you need those changes:

git switch main
git pull

If you have local uncommitted work, check your status first. Do not blindly pull when your working tree contains important unfinished changes.

20. Push

git push sends commits from your local repository to a remote repository.

git push
git push origin main
git push -u origin feature/login-page

The -u option sets the upstream relationship for the branch, making later git push and git pull more convenient.

21. Merge

Merge combines the history of one branch into another branch.

Case 7 — Merge a Feature into Main

git switch main
git pull
git merge feature/login-page

If everything is correct:

git push origin main
In a team using Pull Requests, do not bypass the team's review process by directly merging locally unless that is the agreed workflow.

22. Merge Conflicts

A conflict happens when Git cannot automatically decide how to combine changes, often because different branches changed overlapping parts of a file.

Git marks the conflict in the file using markers such as:

<<<<<<< HEAD
your version
=======
other branch version
>>>>>>> feature/login-page

Case 8 — Resolve a Merge Conflict

  1. Run the merge.
  2. Run git status to see conflicted files.
  3. Open each conflicted file.
  4. Decide what the final code should be.
  5. Remove the conflict markers.
  6. Save the file.
  7. Stage the resolved file.
  8. Complete the merge commit if Git requires it.
git status
git add conflicted-file.html
git commit
Never resolve a conflict by blindly choosing one side. Read both changes and confirm what the final application should do.

23. Rebase

Rebase re-applies commits on top of another base commit. It can create a cleaner, more linear project history, but it rewrites commit history.

Example

git switch feature/login-page
git fetch origin
git rebase origin/main

If conflicts occur, resolve them and then:

git add conflicted-file
git rebase --continue

To cancel the rebase:

git rebase --abort
Important rule: Be careful rebasing commits that other people are already using. Rewriting shared history can cause confusion and may require a force push.

24. Merge vs Rebase

MergeRebase
Combines histories.Re-applies commits on a new base.
Does not rewrite existing commits in the same way.Rewrites commit history for the rebased commits.
Often easier for beginners.Useful when a team understands history rewriting.

25. Undoing Changes — Understand the Difference

Git has several commands for undoing work. They are not interchangeable.

CommandMain purpose
git restoreRestore files in the working tree or staging area.
git resetMove the branch/HEAD or adjust the staging area depending on options.
git revertCreate a new commit that reverses an earlier commit.

26. Case 9 — Discard an Uncommitted File Change

If you changed a file but want to discard the working-tree change:

git restore filename.html
This can permanently discard your uncommitted changes to that file. Check git diff before using it if the work matters.

27. Case 10 — Unstage a File

If you ran git add but do not want the file included in the next commit:

git restore --staged filename.html

This removes the file from the staging area but keeps your working-tree changes.

28. Case 11 — Undo a Commit Safely on a Shared Branch

If a commit has already been shared and you want to reverse its effect:

git revert COMMIT_ID

Git creates a new commit that reverses the selected commit.

For shared history, git revert is generally safer than rewriting history.

29. Reset

git reset can move the current branch to another commit and can also affect the staging area depending on the mode.

Common forms

git reset --soft HEAD~1
git reset --mixed HEAD~1
git reset --hard HEAD~1
ModeBasic idea
--softMove HEAD; changes remain staged.
--mixedMove HEAD and unstage changes; working files remain changed.
--hardMove HEAD and make working files/index match it; can destroy uncommitted work.
Danger: Do not teach git reset --hard as a casual undo command. It can destroy uncommitted work.

30. Stash

Stash temporarily stores uncommitted changes so that you can work on another task without committing unfinished work.

Case 12 — You Must Switch Tasks Suddenly

git status
git stash push -m "WIP login form"
git switch bugfix/navbar

Later:

git switch feature/login-page
git stash list
git stash pop

Useful commands:

git stash list
git stash show
git stash pop
git stash apply
git stash drop

31. Viewing History

git log
git log --oneline
git log --oneline --graph --decorate --all
git show COMMIT_ID

The graph form is particularly useful when learning branches and merges.

32. Case 13 — Find Out What Changed

git status
git diff
git diff --staged
git log --oneline
git show COMMIT_ID
Debugging habit: When something looks wrong, do not immediately change more files. First inspect git status, git diff, and recent commits.

33. Tags

Tags give meaningful names to specific points in Git history, commonly releases.

git tag v1.0.0
git tag
git show v1.0.0

Push a tag:

git push origin v1.0.0

Push all tags:

git push origin --tags

34. GitHub Pull Requests

A Pull Request (PR) is a GitHub collaboration mechanism for proposing changes from one branch into another branch.

Typical flow:

Create branch → Make changes → Commit → Push branch → Open PR → Review → Fix comments → Merge

What should a good PR contain?

  • A clear title.
  • A short explanation of what changed.
  • Why the change was needed.
  • Testing information.
  • Screenshots for UI changes when useful.
  • Small, focused changes rather than unrelated work.

35. Case 14 — Pull Request Workflow

git switch main
git pull
git switch -c feature/product-card

# edit files

git status
git add .
git commit -m "Add product card"
git push -u origin feature/product-card

Now create a Pull Request on GitHub from feature/product-card into the project's target branch.

After review, fix requested changes:

# edit files
git add .
git commit -m "Address product card review"
git push

37. Case 15 — Contribute to a Repository You Cannot Directly Write To

  1. Fork the repository on GitHub.
  2. Clone your fork.
  3. Create a feature branch.
  4. Make and commit your changes.
  5. Push the branch to your fork.
  6. Open a Pull Request from your fork to the original repository.
git clone https://github.com/YOUR-USERNAME/PROJECT.git
cd PROJECT
git switch -c feature/my-change

# edit files

git add .

git push -u origin feature/my-change

38. Upstream Remote for Forks

When working from a fork, teams commonly name the original repository upstream and your fork origin.

git remote add upstream https://github.com/ORIGINAL-OWNER/PROJECT.git
git remote -v

Update information from the original project:

git fetch upstream

Then integrate the desired upstream branch according to the project's workflow.

39. GitHub Issues

Issues can be used to track bugs, tasks, feature requests, questions, and project work.

A useful issue should explain:

  • What is wrong or what is needed.
  • Steps to reproduce a bug when applicable.
  • Expected behavior.
  • Actual behavior.
  • Relevant screenshots, logs, or environment details.

40. README.md

Most GitHub projects have a README.md file that explains the project.

A useful README commonly contains:

  • Project name
  • Description
  • Features
  • Requirements
  • Installation steps
  • How to run the project
  • How to test it
  • Environment variable setup
  • Project structure
  • Contribution instructions

41. GitHub Actions — Basic Awareness

GitHub Actions can automate tasks such as testing, linting, building, and deployment when repository events occur.

A workflow is commonly stored under:

.github/workflows/

Example situations:

  • Run tests whenever a Pull Request is opened.
  • Run linting on every push.
  • Build an application before deployment.
  • Deploy after changes are merged.
For beginners: Understand what CI/CD is and recognize the .github/workflows folder before trying to write complex workflows.

42. Git Aliases

Aliases create shortcuts for frequently used commands.

git config --global alias.st status
git config --global alias.co checkout
git config --global alias.br branch
git config --global alias.lg "log --oneline --graph --decorate --all"

Then:

git st
git br
git lg

43. Case 16 — Accidentally Committed the Wrong File

First, inspect the commit:

git show --stat
git status

If the commit has already been pushed to a shared repository, do not casually rewrite history. Decide whether the file should be removed in a new commit or whether the repository's history must be cleaned using an agreed procedure.

If the accidentally committed file contains a secret, assume the secret is compromised: revoke/rotate the credential first. Removing the file from the latest commit does not automatically make the secret safe.

44. Case 17 — Accidentally Changed the Wrong Branch

If you have uncommitted work and realize you are on the wrong branch, stop before making more changes.

  1. Run git status.
  2. Decide whether the changes should be committed, stashed, or otherwise moved.
  3. Move to the correct branch.
  4. Bring the work over using the appropriate method.

For already committed work, git cherry-pick can copy a specific commit onto another branch:

git switch correct-branch
git cherry-pick COMMIT_ID

45. Cherry-Pick

git cherry-pick applies the changes introduced by selected commits to the current branch.

Use case: A bug fix exists on another branch and you need that specific commit on your release branch.

git switch release
git cherry-pick COMMIT_ID
Cherry-pick can create conflicts and duplicate changes if used carelessly. Use it when you specifically need selected commits, not as a replacement for understanding branch integration.

46. Detached HEAD

Normally, HEAD points to the currently checked-out branch. In a detached HEAD state, you are directly viewing a commit (or another reference) rather than being on a normal branch.

git status

If you made useful commits while detached, create a branch so the commits remain easy to find:

git switch -c recovery-branch
Recovery rule: If Git says you are in a detached HEAD state, do not panic. Check the commit you are on and create a branch if you need to keep your work.

47. Submodules — Basic Awareness

A Git submodule lets one Git repository include another Git repository at a specific commit.

Common commands:

git submodule add https://github.com/OWNER/DEPENDENCY.git path/to/dependency
git submodule update --init --recursive
git submodule status
A submodule is not simply a normal folder copied into the parent repository. The parent repository records a specific commit of the child repository.

48. Line Endings and Cross-Platform Work

Developers on Windows, macOS, and Linux can encounter line-ending differences. Git has configuration options to help manage them.

For example, check:

git config --get core.autocrlf

For team projects, follow the repository's existing configuration and contribution guidelines rather than changing line-ending settings randomly.

49. Git Status as Your Safety Check

Make git status a habit before important operations.

git status

Especially run it before:

  • Switching branches.
  • Pulling.
  • Merging.
  • Rebasing.
  • Resetting.
  • Deleting branches.
  • Creating a Pull Request.

53. Practical Lab — Complete GitHub Exercise

Goal

Create a small website, track it with Git, publish it to GitHub, develop a feature on a branch, and create a Pull Request.

Step 1 — Create a project

mkdir student-git-project
cd student-git-project

Step 2 — Create a simple file

index.html

Step 3 — Initialize Git

git init
git status

Step 4 — Commit the first version

git add .
git commit -m "Create initial website"

Step 5 — Create a GitHub repository

Create an empty GitHub repository and connect it:

git remote add origin https://github.com/USERNAME/student-git-project.git
git branch -M main
git push -u origin main

Step 6 — Create a feature branch

git switch -c feature/about-section

Step 7 — Add the feature

Add an About section to the HTML file, then:

git status
git add .
git commit -m "Add about section"

Step 8 — Push the branch

git push -u origin feature/about-section

Step 9 — Create a Pull Request

Open the Pull Request on GitHub and compare the feature branch with the target branch.

Step 10 — Review and merge

Review the changed files, add a useful description, and merge according to the repository workflow.

54. Practical Lab — Merge Conflict

  1. Create a repository.
  2. Create main with a text file.
  3. Create branch feature-a and change the same line.
  4. Commit the change.
  5. Switch to main and change the same line differently.
  6. Commit the main-branch change.
  7. Merge feature-a.
  8. Observe the conflict.
  9. Resolve the file manually.
  10. Stage and complete the merge.

Learning goal: Students should understand that a merge conflict is not a Git failure. It means Git needs a human to decide what the final code should be.

55. Practical Lab — Undo Practice

Create three commits and deliberately make different mistakes:

  1. Modify a file and use git restore to discard the uncommitted change.
  2. Stage a file and use git restore --staged to unstage it.
  3. Create a commit and use git revert to reverse it.
  4. Create temporary work and practice git stash.

Do this in a practice repository, not in an important production repository.

58. Final Professional Workflow

For most feature-based team projects, a good general pattern is:

# Start from the latest target branch
git switch main
git pull

# Create focused work branch
git switch -c feature/my-feature

# Develop and inspect
git status
git diff

# Save a meaningful version
git add .
git commit -m "Add my feature"

# Publish branch
git push -u origin feature/my-feature

# Open Pull Request on GitHub
# Review → testing → requested changes → approval → merge

# After merging, update local main
git switch main
git pull
Professional habit: Keep commits focused, branches short-lived when practical, commit messages meaningful, and the shared main branch stable.

60. Final Rule to Remember

Git is about managing versions of your code.

GitHub is about sharing those repositories and collaborating with other developers.

When in doubt: check git status before doing anything destructive.
